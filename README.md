# ლექციების ცხრილის ასისტენტი: RAG pipeline (v1) და LangGraph აგენტი (v2)

ჩატბოტი, რომელიც პასუხობს ქართულ კითხვებს უნივერსიტეტის ლექციების ცხრილსა და ჯგუფების სიაზე (ორი PDF). ერთ რეპოზიტორიაში ორი ვერსიაა:

- **v1, RAG pipeline:** ჰიბრიდული ძებნა (ზუსტი ფილტრები და ვექტორული ძებნა), შემდეგ LLM-ის პასუხი.
- **v2, LangGraph აგენტი:** LLM თვითონ ირჩევს SQL-ზე დაფუძნებულ ხელსაწყოებს (tools), იმახსოვრებს საუბარს და პასუხობს იმ კითხვებს, რასაც v1 ვერ პასუხობდა.

> _აქ ჩასვი სკრინშოტები: `docs/chat-group-day.png` (v1 ინტერფეისი წყაროებით) და `docs/agent-terminal.png` (v2, tool-ების გამოძახება და გაგრძელების კითხვა)._

## რას აკეთებს

- `ჯგუფი 103-ს ორშაბათს რა აქვს?`
- `რა ხდება ორშაბათს 10 საათზე?`
- `სად არის ოპტიმიზაციის მეთოდები?`
- მხოლოდ v2: `რამდენი ლექცია აქვს ჯგუფ 103-ს კვირაში?` (დათვლა) და გაგრძელების კითხვები, მაგალითად `და სამშაბათს?`

თუ ინფორმაცია მონაცემებში არ არის (ლექტორი, გამოცდის თარიღი, არარსებული ჯგუფი), ბოტი ამას ამბობს და პასუხს არ იგონებს.

## არქიტექტურა

### v1: pipeline

```
timetable.pdf ──┐
                ├─> parse_pdf.py ─> lessons.json (150 ჩანაწერი, სპეციალობის სახელებით)
groups.pdf ─────┘                          │
                                           v
                          ingest.py: multilingual-e5-base embedding -> ChromaDB
 კითხვა ─> retriever.py ───────────────────┤
              │ ზუსტი რეჟიმი: ჯგუფი / დღე / აუდიტორია / დრო კოდით
              │ სემანტიკური რეჟიმი: ვექტორული ძებნა, როცა ფილტრი არ არის
              v
         rag_chain.py: პრომპტი -> Groq LLM -> ქართული პასუხი
              v
         streamlit_app.py: ჩატი და მოძიებული წყაროები
```

### v2: აგენტი (`src/agent/`)

```
lessons.json -> db.py -> SQLite
შეტყობინება -> [agent node: LLM + tools] --tool-ის გამოძახება--> [tools node: SQL] -> უკან agent-ში
                      │ (tool-ის გარეშე)
                      v
                 საბოლოო პასუხი      (საუბრის მდგომარეობა thread_id-ის მიხედვით = მეხსიერება)
```

ხელსაწყოები: `get_schedule`, `whats_on` (დღე / დრო / აუდიტორია), `find_subject`, `get_group_info`, `count_lessons`, `list_subjects`. აგებულია LangGraph-ზე (`StateGraph`, `ToolNode`, conditional edge, `MemorySaver`).

## დიზაინის გადაწყვეტილებები

- **ერთი ლექცია = ერთი chunk**, ფიქსირებული ზომით დაჭრის ნაცვლად. ცხრილი სტრუქტურირებული მონაცემია, ამიტომ ყოველი ლექცია იშლება ველებად (`day, start, end, subject, group, room, type`).
- **ორი PDF გაერთიანებულია:** ლექციას ჯგუფის სპეციალობის სახელიც ახლავს, ამიტომ "პროგრამული ინჟინერიის სტუდენტებს სამშაბათს რა აქვთ?" ჯგუფ 103-ზე გადადის.
- **ზუსტი პირობები კოდშია და არა embedding-ში.** embedding არ "ხვდება", რომ 10:00 ხვდება 09:00–10:20 ინტერვალში, ამიტომ ჯგუფი, დღე, აუდიტორია და დრო კოდით იფილტრება.
- **ქართული ენა:** PDF-ის ტექსტი სწორად იკითხება (OCR არ დასჭირდა), გამოყენებულია მრავალენოვანი embedding მოდელი, დღეები მოიძებნება ფუძით, რადგან ქართული ბრუნდება.
- **დაფუძნებული პასუხი:** მოდელი პასუხობს მხოლოდ მოძიებულ ჩანაწერებზე ან tool-ის შედეგზე და ამბობს, როცა ვერ პოულობს.
- **მოდელის გამოსავლის გადამოწმება (v2):** tool-ის არგუმენტები (დღე, ლექციის ტიპი) მოწმდება ბაზის რეალურ მნიშვნელობებზე, რადგან LLM ყოველთვის სუფთა ტექსტს არ აბრუნებს (იხ. ქვემოთ).

## შეფასება

### v1: 30 კითხვა, 7 კატეგორია

| `openai/gpt-oss-20b` | 25/30 (83.3%) | სუსტია, როცა რამდენიდან ერთი ჩანაწერი უნდა აირჩიოს |

### შეფასებით ნაპოვნი პრობლემები

- **v1: ჯგუფის ნომერი აუდიტორიად იკითხებოდა.** regex-მა "ჯგუფი 105"-ში 105 აუდიტორიად აღიქვა. გასწორების შემდეგ "ჯგუფი + დღე" კითხვები 6/8-დან 8/8-ზე გადავიდა.
- **v1: დროის კითხვები.** სუფთა ვექტორულმა ძებნამ "ორშაბათს 10:00-ზე" ლექციები გამოტოვა; ინტერვალის შემოწმება კოდში გადავიტანე.
- **v2: ბერძნული ასოები ქართულ tool-არგუმენტში.** მოდელმა გადასცა `'პρακτიკული სამუშაო'` (ბერძნული ასოებით), ზუსტმა SQL შედარებამ 0 დააბრუნა და აგენტმა თქვა, რომ პრაქტიკული სამუშაო არ არის. გამოსწორება: არგუმენტი მოწმდება ბაზის რეალურ მნიშვნელობებზე და შეცდომისას ბრუნდება სწორი ვარიანტების სია.
- **v2: გამოტოვებული ჩანაწერები.** "რა არის ორშაბათს 10:00-ზე" tool-მა 6 ლექცია დააბრუნა, მოდელმა 1 ჩამოთვალა. გამოსწორება: tool-ის გამოსავალი ჩანაწერების რაოდენობას აცხადებს და პრომპტი ითხოვს ყველას ჩამოთვლას.
- **v2: მისალმება "ვერ ვიპოვე"-ს ნაცვლად.** "როდის არის გამოცდა?"-ზე აგენტმა მისალმებით უპასუხა. გამოსწორება: პრომპტის წესები დავაზუსტე.
- **ზედმეტად მკაცრი ტესტი** (v1 და v2): სწორი პასუხები ჩავარდნილად ითვლებოდა, რადგან ტესტი სპეციალობის სახელს მხოლოდ ერთ ენაზე ელოდა. ტესტის შეცვლამდე პასუხები ხელით გადავამოწმე.

## შეზღუდვები

- ტესტები იმავე დაპარსული მონაცემებიდანაა დაგენერირებული და ფორმულირება ერთგვაროვანია, ამიტომ ეს regression ტესტებია და არა დამოუკიდებელი benchmark. რეალური მომხმარებლის ფორმულირება (შეცდომები, სლენგი) მხოლოდ ნაწილობრივ არის დაფარული.
- v2-ის სატესტო ნაკრები მცირეა (12 კითხვა), ერთი კითხვა დაახლოებით 8 პროცენტულ პუნქტს ცვლის.
- შედეგები გაშვებებს შორის იცვლება, რადგან LLM არადეტერმინისტულია.
- **აგენტი ორიგინალურ 30 კითხვაზე v1-ზე სუსტია (76.7–83.3% vs 96.7%), განსაკუთრებით საგნის ძებნაში (0/4). მიზეზი ჯერ არ არის გამოკვლეული.**
- ერთი ცხრილი, ლექტორისა და გამოცდების მონაცემები წყაროში არ არის.
- არ არის განხორციელებული: MCP სერვერი, ხმოვანი შეყვანა.

## ტექნოლოგიები

Python 3.12 · pdfplumber · sentence-transformers (`intfloat/multilingual-e5-base`) · ChromaDB · SQLite · LangGraph · langchain-groq · Groq API (`openai/gpt-oss-120b`) · Streamlit

## გაშვება

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows (macOS/Linux: source .venv/bin/activate)
pip install -r requirements.txt
```

შექმენი `.env` ფაილი ხაზით `GROQ_API_KEY=შენი_გასაღები`, PDF-ები ჩააგდე `data/raw/`-ში (`timetable.pdf` და `groups.pdf`), შემდეგ:

```bash
python src/parse_pdf.py                # PDF -> data/processed/*.json
python src/ingest.py                   # v1: ვექტორული ინდექსის აგება
streamlit run app/streamlit_app.py     # v1: ჩატის ინტერფეისი
python src/agent/db.py                 # v2: SQLite ცხრილის აგება
python src/agent/run_agent.py          # v2: აგენტის ჩატი ტერმინალში
python tests/build_eval.py             # 30 სატესტო კითხვის გენერაცია
python tests/run_eval.py               # v1 შეფასება (არჩევითად მიუთითე მოდელის სახელი)
python tests/run_agent_eval.py         # v2 შეფასება (12 კითხვა)
python tests/run_eval_agent_on_30.py   # ორიგინალური 30 კითხვა აგენტზე
```

## შესაძლო გაუმჯობესებები

აგენტის საგნის ძებნის გამოკვლევა და გასწორება, tool-ების MCP სერვერად გამოქვეყნება, ხმოვანი შეყვანა (Whisper), აგენტის Streamlit ინტერფეისთან დაკავშირება, ხელით დაწერილი უფრო რთული სატესტო ნაკრები რეალური ფორმულირებით, FastAPI და Docker.
